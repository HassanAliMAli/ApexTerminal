# Run database migrations

The API's tables change from release to release. Each migration is an Alembic revision in `backend-api/backend/alembic/versions`. The migrations run before the API starts, so each release meets the schema it expects. This guide explains how replicas coordinate migrations and how to check a database or prepare a first deployment.

## When the migrations run

Run `python api_entrypoint.py` from `backend-api/backend` in the API's Python environment. It runs `python -m alembic upgrade head` and then starts the API. If a migration fails, it logs "Database migrations failed" and exits with status 1 before serving requests. The upgrade applies missing revisions in order.

A deployment with several replicas can also run `python -m alembic upgrade head` as a one-off job before restarting them. The command can be repeated on a database that is already current.

## Several replicas at once {#several-containers-at-once}

For MySQL and PostgreSQL, the migrations coordinate through the `alembic_migrations` lock in Valkey. The first process to acquire the lock holds it for at most <SettingConstant name="migrationLockSeconds" unit="min" />. Other replicas log "Another migration in progress by pod" and retry every <SettingConstant name="migrationPollSeconds" unit="s" />. After migration, a marker makes the others log "Migrations already applied, skipping..." for the next <SettingConstant name="migrationDoneSeconds" unit="s" />. [Connect FINOS Workspace to its database and cache](connect-the-database-and-cache.md) covers Valkey connectivity. SQLite serves a single machine and requires no Valkey migration lock.

## Run the migrations yourself

Run Alembic from `backend-api/backend` with the same Python and settings as the API:

```bash
python -m alembic upgrade head
```

To see which revision the database applied and which revisions the release contains, use:

```bash
python -m alembic current
python -m alembic history
```

Alembic prints the identifier of each revision. A database that is behind has a current revision that is older than the newest one of the history, and `upgrade head` brings it to the newest.

## Upgrade a deployment

1. Back up the database, because a migration changes the data in place, and some revisions remove columns that nothing reads any more.
2. Roll out the new release. The startup command runs migrations before the first API process starts.
3. Check that the API's log says "Database migrations completed successfully", and that `/health` answers.

Roll out the API and worker replicas together so they use the same schema. Check compatibility before rolling back to an earlier release against a migrated database.

## Prepare a first deployment

On an empty database, the same step creates every table. The deployment also needs its first organization and administrator, which the script `scripts.init_users` creates from the file `scripts/cfgs/config.toml`: the file names the organization and the administrators, and the script creates them when they do not exist, creates the roles and sets the `DEFAULT_USER_MAPPING` that new people receive in the file `user_create.json`. The script is safe to run on every start, and a run that finds everything in place changes nothing. [Provision an organization from a file](provision-an-organization.mdx) is the way to create further organizations, and the administrator gets a password with the command `python -m scripts.init_users --new-password <email>`, as [Run FINOS Workspace on your machine](../build-from-source/run-the-stack-from-source.md#set-the-administrators-password) shows.
